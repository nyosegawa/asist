# ASIST から何も読まない音声のプロセスは、Mac では見張りのシェルで ASIST と一緒に終わらせる

音声認識の llama-server と、ASIST が起動した VOICEVOX と AivisSpeech のエンジンは、ASIST から何も読まないので、ASIST が終了の手順を通らずに終わると、Mac では親が launchd に変わって動き続け、モデルのメモリを持ったままになる。強制終了やクラッシュのほか、開発中に起動したアプリを止めたときにも起きる。そこで Mac では、これらを自分のプロセスグループで起動し、Agent と同じ見張りのシェルをつける。見張りは ASIST だけが書くパイプを読み、プロセスが自分で終わったときは ASIST が 1 行書いて見張りも終わり、1 行が来ないままパイプが閉じたときは、そのグループに SIGTERM を送る。見張りを起動できないときは、ASIST が落ちたら残るプロセスを作らないように、そのプロセスを起動しない。標準入力から要求を読む speech.cpp のワーカー、Python のワーカー、マイクの補助のプログラムは、ASIST が終わるとパイプが閉じて自分で終わるので、見張りはつけない。Windows では何もしない。libuv が、`detached` を付けずに起動した子プロセスを、ASIST と一緒に閉じる Job Object に入れるからである。

## 見送った案

- **次に起動したときに、前回残ったプロセスを探して止める。** 次に起動するまで、残ったプロセスがメモリを使い続ける。
- **llama-server をシェルで包み、シェルが標準入力の終わりを読んだら llama-server を止める。** ASIST が持つのがシェルのプロセスになり、llama-server が落ちたことを知るにも、止めるときに信号を llama-server まで届けるにも、シェルにもう一段の仕組みが要る。
- **見張りを起動できなくても、プロセスは起動する。** ASIST が落ちたときに残るプロセスを、そうと知りながら作ることになる。Agent と同じく起動しない。

## 実測

- 2026-10-05、Apple M5 の macOS 26.2 で、マイクを入れて全部のモデルを読み込んだ ASIST の本体を `kill -9` で止めると、10 秒後には llama-server だけが残っていた。speech.cpp のワーカー、Python のワーカー 3 つ、マイクの補助のプログラムは終わっていた。別の worktree で開発中に起動した llama-server は、親が launchd のまま 2 日 14 時間動いていた。
- 同じ日、同じ Mac で、VOICEVOX と AivisSpeech のエンジンを ASIST と同じように起動した Node のプロセスを `kill -9` で止めると、どちらのエンジンも 12 秒後に親が launchd のまま動いていた。この決まりで起動すると、どちらも親と一緒に終わった。
- 同じ日、RTX 2080 の Windows 11 で、モデルを読み込んだ ASIST の本体を `Stop-Process -Force` で止めると、10 秒後には llama-server を含む子プロセスがすべて終わり、VRAM は 1682 MB に戻っていた。

## 分かっている制約

- 見張りが送るのは SIGTERM だけである。SIGTERM で終わらないプロセスは残る。
- これらのプロセスは自分のプロセスグループで動くので、開発中にターミナルで Ctrl-C を押しても SIGINT は届かず、Electron が終わったあとに見張りが止める。
- この決まりより前のビルドが残したプロセスは止めない。
