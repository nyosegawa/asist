# CI はビューアの計測を、ふだんの値から大きく離れたときだけ失敗にし、細かく決めた予算は報告するだけにする

ファイルのカードのビューアを大きなファイルで測る `npm run demo:viewer-budgets` は、CI では、ビューアがファイル全体を読んだり描いたりする以前のやり方に戻ったことを見つけるために動かす。以前のやり方は、表示までに何秒もかかり、メモリを何 GB も増やしていた。CI を失敗にするのは、共有の runner で同じコードが動く幅から十分に離れた上限を超えたときだけにする。表示まで 5 秒、画面のスレッドが止まる時間 2 秒、拡大表示の 1 画面が出るまで 3 秒、メモリの増え方は最大で 1.5 GB、最後に 1 GB、GPU で 1 GB が上限で、上限の値はシーンのコメントに書く。上限だけでは以前のやり方に戻っても通ってしまう case には、その case だけの確認を足す。開発に使う Mac で決めた細かい予算は、case に残して結果と並べて報告するが、超えても CI は失敗にしない。ビューアを直す Agent が、変更の前と後を手元で比べるための数字として使う。

## 見送った案

- **CI を細かい予算で失敗させる。** 予算は開発に使う Mac で決めた数字で、共有の runner では同じコミットでもその外に出た。2026-10-02 と 03 に失敗した 13 の job のうち 10 がこの計測で、そのうち 4 つはビューアに触れていない変更だった。利用者は 2026-10-03 に、これを「シビアすぎる」と判断した。予算を少し超えただけで CI が失敗しても、それはビューアの不具合を指していない。

## 実測

- 共有の runner(GitHub Actions の macos-latest)での 91 回、2026-10-02 と 03 の main とプルリクエスト。表示までは最長 2.0 秒(99 パーセンタイルで 1.2 秒)、画面のスレッドが止まったのは最長 781 ms(同じく 270 ms)、1 画面は最長 820 ms、レンダラーのメモリは最大で +699 MB、最後に +416 MB、GPU は +217 MB だった。同じコミットを 2 回測ると、5 万行の Excel の拡大表示でスレッドが止まった時間は 781 ms と 64 ms、200 枚のスライドのメモリの最大は +494 MB と +374 MB だった。
- 以前のやり方(Apple M5、ファイルの大きさの制限を外して測った値)。300 ページの Word は表示まで 24 秒で +2.5 GB、200 枚のスライドは 8.5 秒で +1.9 GB、2 時間の MP3 は 15.6 秒で +9.6 GB、1 時間の WAV は 4.6 秒で +10.5 GB、200 ページの PDF は +5.1 GB で GPU が +1.4 GB だった。Excel は、5 枚のシートのものが表示まで 5.3 秒でスレッドが 2.6〜2.7 秒止まり、5 万行のものは 1.4 秒、0.8 秒、+0.54 GB で上限の中に収まる。

## 分かっている制約

- 上限より小さい後退は CI では見つからない。ビューアを変えるときは、手元で予算と比べる。
- 5 万行の Excel のように、以前のやり方でも上限の中に収まる case は、時間とメモリでは後退を見つけられない。その case には、拡大表示の終わりにシートの最後の行が出ていることのように、以前のやり方が満たさない確認を足しておく。
