# ローカルの音声認識は、読み上げと同じ speech.cpp のワーカーで動かし、llama.cpp は同梱しない

ローカルの音声認識の Qwen3-ASR(1.7B と 0.6B)は、読み上げと同じく、同梱した speech.cpp の `speech worker` で動かす。ワーカーは 1 つのモデルしか動かさないので、音声認識のワーカーを読み上げのワーカーとは別に起動し、どちらにも同じワーカーのプロトコルのクライアントで要求を送る。モデルは `sakasegawa/Qwen3-ASR-1.7B-GGUF` と `sakasegawa/Qwen3-ASR-0.6B-GGUF` の GGUF のファイルを 1 つずつ、リビジョンと sha256 を固定して取得する。会話の言語は BCP 47 のタグ(`ja` など)で speech.cpp の `language` に渡し、公式の実装と同じ答えの書き出し(`language Japanese<asr_text>`)は speech.cpp が書く。llama.cpp の llama-server は同梱しない。llama-server で動かすと、speech.cpp とは別の実行環境をもう一つ持つことになる。ggml-org のモデルと mmproj の 2 つのファイル、ループバックのポートとその鍵、Mac での見張り(ADR 0056)が要り、文脈は 4096 トークンで、約 270 秒より長い発話は失敗した。llama.cpp の Qwen3-ASR は公式の実装とも違い、プロンプトに system の発言が無く、log-mel のフレームが 1 つ多く、最後の 1 秒に満たない音声からゼロで埋めた分の音声トークンを作る。speech.cpp は公式のプロンプトで公式と同じ文を書き、下の実測のとおり、デコードの速さと書き起こしの精度は llama.cpp と変わらない。

## 見送った案

- **音声認識は llama.cpp の llama-server で動かし続ける。** 上に書いた別の実行環境と 270 秒の上限が残り、公式の実装と違う文を書く発話も残る。デコードの速さと書き起こしの精度は、下の実測のとおり speech.cpp と変わらない。

## 実測

- 2026-10-07、Apple M5(32 GB)、Metal、Q8_0。speech.cpp 0.7.1 と、ASIST が同梱していた llama.cpp b11246 に同じ FLEURS の発話を交互に聞かせ、5 回(1.7B は 3 回)の中央値。言語は指定した。

  | 発話 | 0.6B、speech.cpp | 0.6B、llama.cpp | 1.7B、speech.cpp | 1.7B、llama.cpp |
  |---|---|---|---|---|
  | 日本語、6.36 秒 | 0.17 秒 | 0.16 秒 | 0.38 秒 | 0.44 秒 |
  | 日本語、10.50 秒 | 0.25 秒 | 0.23 秒 | 0.59 秒 | 0.58 秒 |
  | ドイツ語、11.16 秒 | 0.32 秒 | 0.30 秒 | 0.74 秒 | 0.71 秒 |
  | 英語、23.64 秒 | 0.59 秒 | 0.51 秒 | 1.36 秒 | 1.20 秒 |
  | 日本語、25.50 秒 | 0.80 秒 | 0.75 秒 | 1.89 秒 | 1.76 秒 |

  デコードは、0.6B で 1 秒に 146〜158 トークン(llama.cpp は 147〜157)、1.7B で 58〜63 トークン(同じく 58〜62)だった。残る差はエンコーダとプロンプトの読み込みで、llama.cpp は Metal 4 の tensor API で行列の積を計算し、speech.cpp は ggml のカーネルの不具合のためにそれを使わない。同じ 20 の要求で、llama.cpp は 0.6B で 6、1.7B で 4 の要求に公式と違う文を書いた。
- 同じ日、同じ Mac で、ASIST の音声認識のクライアントから speech.cpp 0.7.1 のワーカーに FLEURS の日本語と英語の 7 つの録音を言語を指定して書き起こさせると、どちらの大きさも、ほぼ無音の 0.6 秒の録音のほかはすべて公式の文と同じだった。ほぼ無音の録音は、ワーカーに渡す 16 ビットの値に丸めると最大の振幅が 10 段ほどになり、どちらの大きさも公式と違う文を書いた。丸めずに渡すと、1.7B は公式と同じ文を書いた。かかった時間は 3 回で、1.7B が 10.50 秒の発話に 0.62〜0.74 秒、25.50 秒の発話に 2.1〜2.6 秒、0.6B が 0.27〜0.31 秒と 0.87〜1.01 秒だった。準備ができるまでは、ファイルが OS のキャッシュにある状態で 1.7B が 0.56〜0.67 秒、0.6B が 0.37〜0.42 秒、メモリは 25.50 秒の発話を書き起こしたあとで 1.7B が 2.5 GB、0.6B が 1.1 GB だった(2026-09-29 の llama-server は 3.4 GB と 1.8 GB)。
- 2026-10-07、RTX 2080(8 GB)の Windows 11、Vulkan。Common Voice 8.0 の日本語の 4,483 のクリップを、言語を `ja` にして speech.cpp 0.7.0 と llama.cpp b11246 に書き起こさせた(speech-bench の asr-runtimes-on-common-voice-8-ja-2026-10-07)。認められた表記を許した文字の誤り率は、1.7B が 4.52%(llama.cpp は 4.56%)、0.6B が 6.88%(同じく 6.88%)だった。待ち時間の中央値は 1.7B が 0.203 秒(0.192 秒)、0.6B が 0.126 秒(0.121 秒)、読み込みは 1.7B が 2.2 秒(3.2 秒)、0.6B が 2.3 秒(4.2 秒)だった。同じ RTX 2080 で、speech.cpp 0.7.1 は 0.7.0 より、FLEURS の 5 つの発話を 13〜25% 速く書き起こした。

## 分かっている制約

- 1 つの要求で一度に聞けるのは 1200 秒までで、それより長い音声は speech.cpp が分けて聞く。1 つの部分が 4096 トークンに達すると、そこまでの文を返す。
- 途中の書き起こしは、これまでどおり最後の 5 秒を毎回新しい要求として送る。話しているあいだに音声をワーカーに送り続けて `peek` で読む形は、まだ使っていない。
- speech.cpp は ASIST のために作ったもので、Qwen3-ASR の新しい版にも自分で追従する。
