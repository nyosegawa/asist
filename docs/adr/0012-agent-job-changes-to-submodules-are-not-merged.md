# エージェントのジョブがサブモジュールに加えた変更は取り込まず、取り込まないことを利用者に伝え、worktree ごと残す

worktree で隔離したジョブの変更をまとめるとき、サブモジュールの項目(サブモジュールが指すコミット)と .gitmodules は、利用者のリポジトリのいまの HEAD とジョブのブランチの合流点(merge base)のままにしてコミットする。その項目のパスの下にあるファイルも同じにする。サブモジュールの中のファイルの変更も、サブモジュールの追加や削除も取り込まない。新しい worktree ではサブモジュールが初期化されておらず、エージェントが初期化してその中でコミットしても、そのコミットは worktree の中のサブモジュールの複製にしか無く、worktree を片付けると消える。サブモジュールが指すコミットだけを取り込むと、利用者のリポジトリは存在しないコミットを指すことになる。また、取り込む前に見せる差分には「Subproject commit」の行が出るだけで、サブモジュールの中で何が変わったかは見えないので、利用者が差分を見て承認するという取り込みの前提が成り立たない。

ジョブの変更は、ジョブを始めたコミットではなく合流点から数える。取り込みが利用者のブランチに加えるのは合流点からの変更なので、承認のために見せる差分もそれと同じにする。エージェントが利用者のブランチを取り込んだり、その上にリベースしたりすると、ブランチには利用者自身のコミットも入る。そこでのサブモジュールの変更は利用者のものなので、元に戻さない。

取り込まなかったサブモジュールは、ジョブが終わったときに調べてジョブに記録し、取り込み待ちの差分、取り込みと破棄の確認画面、ジョブの報告で名前を伝える。サブモジュールの変更があるジョブは、ほかに変更がなくても worktree を片付けず、取り込み待ちとして残す。その変更は worktree にしか無いので、消えるのは利用者が取り込むか捨てると決めたときだけで、確認画面にもそのことを書く。

## 見送った案

- **サブモジュールの中の変更をサブモジュールのリポジトリへ移して取り込む。** 取り込みの確認画面で見せる差分にサブモジュールの中の変更が出ず、利用者が見ていない変更を利用者の別のリポジトリへ書き込むことになる。
- **サブモジュールに変更があれば、ほかの変更も含めて取り込みを止める。** サブモジュールの外の変更まで、続きのジョブでサブモジュールの変更を戻させるまで取り込めなくなる。
- **サブモジュールの項目を、ジョブを始めたコミットのままにする。** エージェントが利用者のブランチを取り込んだあとだと、利用者が自分で進めたサブモジュールを取り込みが元に戻してしまい、見せた差分にもそれが出ない。
- **サブモジュールの中だけが変わったジョブを、変更のないジョブとして worktree ごと片付ける。** エージェントのコミットの唯一の複製を、利用者に聞かずに消すことになる。

## 分かっている制約

- ジョブでサブモジュールが指すコミットを新しくする(依存を最新にする)ことはできない。
- サブモジュールの中だけが変わったジョブには取り込めるものがなく、捨てるか、続きのジョブで変更をサブモジュールの外へ移すしかない。
