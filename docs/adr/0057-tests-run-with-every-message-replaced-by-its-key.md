# テストは辞書のすべてのメッセージをキーに置き換えて走らせ、辞書の書き写しはそのテスト自身の失敗で見つける

テストのあいだ、辞書のメッセージはすべて、言語とキーを書いた文字(`‹ja-JP common.save›`)とプレースホルダーと改行だけになる。画面の言葉を確かめるテストは `t('key')` で辞書から読むので、そのまま通る。辞書の言葉を書き写したテストは、書き写した場所で落ちる。モデルに渡す文、保存するファイルの決まった形、テストのデータのように、辞書から来ない文字は置き換えの影響を受けない。テストの日本語が辞書の言葉かどうかは、綴りでは決められず、その文字がどこから来たかで決まるからである。同じ「晴れ」でも、天気カードのラベルなら辞書の言葉で、気象庁のデータならデータである。辞書の言葉そのものを確かめるテスト(`tests/i18n.test.ts`)だけが本物の辞書を読む。

## 見送った案

- **テストに書かれた日本語が辞書のどれかと同じ綴りならエラーにする。** 以前はこの形だった。データがたまたま辞書の言葉と同じだと誤ってエラーになり、例外の一覧が増え続けた。どこかの画面で辞書に言葉を足しただけで、関係のないテストが落ちることもあった。一方で、数と組み合わせた文や文の一部、`aria-label` でボタンを探す書き方は、綴りが一致しないので見逃した。
- **綴りで照らし合わせる相手を、テストが import するコードが使うキーに絞る。** 誤ってエラーにする件は減るが、辞書の中身で判断する性質は変わらず、文の一部を書き写したものは見逃したままになる。
- **`expect(...)` の中など、画面の文字と比べる場所の文字列だけを見る。** `aria-label` でボタンを探すような、アサーションの外での書き写しを見逃す。

## 実測

2026-10-05 に置き換えを入れたとき、綴りで照らし合わせるチェックが通していたテストのうち 28 件が落ち、すべてが辞書の書き写しだった(「14ターン」「2件」「1分05秒で完了」、英語の「Done」「Tomorrow」、日本語の `aria-label` で探すボタンなど)。デモのデータがファイルの無いときのエラー文を日本語でじかに持っていたことも、これで分かった。以前のチェックの例外の一覧にあった 24 件は、どれも置き換えの影響を受けなかった。同じ日に数えると、テストにある `t()` 789 件のうち 291 件はアサーションの外にあった。

## 分かっている制約

- 書き写した文字を「無いこと」で確かめるテスト(`not.toContain('…')`、日本語の `aria-label` で探して `toBeNull()`)は、置き換えても落ちず、意味を失ったまま通る。
- 本物の文がどう振る舞うかを確かめるテスト、たとえばそれぞれの言語の文で行がどこで折れるかを見るテストは、そのファイルで本物の辞書に戻さなければ書けない。
