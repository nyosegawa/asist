# 保存する JSON のファイルは形式の版を持ち、読むときに今の版へ移す

userData に保存する JSON のファイル(設定、タスク、タイマー、ジョブ、記憶の整理の状態、API の使用量、プロジェクトの一覧、メールの下書き、暗号化したキーとパスワード)は、先頭の `version` に形式の版を書く。`version` のないファイルは版を書く前の形式で、版1として扱う。形式を変えるときは、項目を1つ足すだけでも版を上げ、前の版から移す関数を足す。移す関数は消さずに積み重ねる。読むときに古い版なら、元のファイルを `<名前>.v<版>.json` として残してから順に移して書き直す。アプリが知っているより新しい版なら、読まずに止める。人に配ったあとは、形式を変えるたびに利用者のアプリが起動しなくなり、利用者が手でファイルを直すしかなくなるからである。新しい版のファイルを古いアプリが読むと、知らない項目を落として書き戻すおそれがある。

## 見送った案

- **形式が変わったら古いファイルを捨てる。** 開発のあいだはこの方針で、移す関数を持たずに済んだ。配布したあとは、利用者の設定やタスクが失われる。
- **項目を足すだけの変更では版を上げない。** 新しいアプリは既定値で読めるが、古いアプリは新しいファイルを知らない項目のせいで拒み、壊れたファイルと見分けられない。

## 分かっている制約

- 記憶とメモの Markdown は移さない。利用者が手で直す文書なので、形式の決まりを変えるときは、記憶の整理の Agent に書き直させる。
- 会話ログとジョブのログ(JSONL)、メールのキャッシュと記憶の索引(SQLite)は、この仕組みに含まれない。
