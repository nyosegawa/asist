# 音声の波形は MP3、AAC、WAV にだけ描き、FLAC と OGG は波形を出さずに再生する

ファイルのカードは、音声の波形をプレビューのページの中で作る。ファイルを先頭から 4 MB ずつ順に読み、WAV はサンプルをそのまま読み、MP3 と AAC(ADTS の .aac と MPEG-4 の .m4a)はフレームに分けて WebCodecs の AudioDecoder で復号する。録音はどれも、ヘッダーが示す長さを 2,000 に分けた区間ごとの最大の振幅として持つので、録音がどれだけ長くても使うメモリは変わらない。そのため、音声には大きさの上限も、ほかのビューアが持つ最後の安全網も置かない。FLAC と OGG には波形を出さず、再生だけをする。MP3、AAC、WAV は、フレームのヘッダーや MPEG-4 のサンプルの表から自分で分けられるが、FLAC と Ogg を分けるには、それぞれの形式に合わせた demuxer を書いて保守し続けることになる。ファイルのカードに出てくる音声の中で FLAC と OGG は多くないので、その手間をかけない。

## 見送った案

- **FLAC と Ogg も自前の demuxer でフレームに分け、AudioDecoder に渡す。** Chromium の AudioDecoder は FLAC も Vorbis も Opus も復号できるが、FLAC は STREAMINFO を description として渡す必要があり(Chrome 154 は description のない設定を「description is required」で断った)、フレームの境目は同期の符号と CRC で探すことになる。Ogg はページをつないでパケットに戻し、Vorbis なら最初のヘッダーのパケットも扱う必要がある。形式ごとに書いて保守する量に比べて、使われる場面が少ない。

## 実測

2026-10-02、Apple M5(メモリ 32 GB)、headless Chrome 154、demo の `npm run demo:viewer-budgets`。ほかの作業でロードアベレージが 33〜45 のときに測った。

- 2 時間の MP3(128 kbps、110 MB)は、最初のピークが 139 ms で描かれ、波形全体は 12.2 秒で描き終わった。renderer のメモリは最大で +255 MB、画面のスレッドが止まったのは最長 23 ms だった。1 時間の m4a(AAC 64 kbps、29 MB)は 4.6 秒で +163 MB、1 時間の WAV(606 MB)は 3.8 秒で +251 MB だった。この値には、プレビューのページの iframe 自体が使う約 160 MB が含まれる。
- 以前のように画面の中でファイル全体を decodeAudioData すると(ロードアベレージ 18 のとき)、2 時間の MP3 は描くまでに 15.6 秒かかり、renderer のメモリは +9,567 MB になり、画面のスレッドは 812 ms 止まった。1 時間の WAV は +10,494 MB だった。
- CI の macos-latest では、2 時間の MP3 の波形を描き終えるまでに 32.7 秒かかった。

## 分かっている制約

- FLAC と OGG のカードには「この形式では波形を出しません」と出る。ADPCM の WAV、Apple Lossless のような AAC 以外の MPEG-4、Chromium の復号器が受け付けない free format の MP3 も同じになる。
- 長い録音は、波形が左から伸びていき、描き終わるまでに時間がかかる。2 時間の MP3 では、この Mac で 10 秒あまりかかる。
- 長さをヘッダーから決められない MP3(Xing フレームのない可変ビットレート)は、描いている途中の横の長さが実際と違うことがある。描き終わった時点で、復号した長さに合わせて描き直す。
